Scaffold a new vertical-slice feature for: $ARGUMENTS

Expected input: `<ModuleName> <AggregateFolder>[/<ChildEntityFolder>] <FeatureName> <command|query>`, e.g. `/add-feature UserAccess Users DeactivateUser command` or `/add-feature DeviceManagement Manufacturers/DeviceModels Rename command`. Ask the user for whatever is missing before generating anything — don't guess the module, aggregate, or verb.

**Child entity of an aggregate** (the optional `/<ChildEntity>` segment — `Manufacturers/DeviceModels` is the one instance today): every `<Aggregate>/` path below becomes `<Aggregate>/<ChildEntity>/`, mirrored in every layer, and the nested feature folders use the aggregate vocabulary (`Add`, `GetOne`, `GetList`) rather than repeating the entity name — `Manufacturers/DeviceModels/Commands/Add/AddDeviceModelCommand.cs`, not `Commands/AddDeviceModel/`. The *types* keep the entity name (`AddDeviceModelCommand`, `GetDeviceModelByIdQueryCommand`). A child entity has no write-side repository (writes go through the root's behaviour and the root's repository) but does get its own read-side one: `Sergin.<Module>.Infrastructure/<Aggregate>/<ChildEntity>/Repositories/Queries/<ChildEntity>QueryRepository.cs` implementing an `I<ChildEntity>AllQueryRepository` in `Sergin.<Module>.Application/<Aggregate>/<ChildEntity>/`. Registration and endpoint mapping stay in the **aggregate's** `<Aggregate>InstallationExtensions` — there is no per-entity installation class. Never create a top-level `<ChildEntity>/` sibling of the aggregate folder; that reads as a second aggregate. Design: `docs/superpowers/specs/2026-09-17-child-entity-folder-layout-design.md`.

This repo has no scaffolding CLI; slices are hand-authored following a strict, repeated shape. Use `src/Modules/UserAccess/**/Users/**` as the reference implementation for the Application, Infrastructure and endpoint files below — read the matching file there before writing the new one, and match its style exactly (sealed records, primary constructors, `ErrorOr<T>` returns, no comments). Two exceptions: for a root that is audited, soft-deletable, versioned or scoped, copy the matching `src/Modules/DeviceManagement/**/Devices/**` file (see "Aggregate features" below), and for the UI copy DeviceManagement's views, not UserAccess's pages.

## Layout to create (module = e.g. `UserAccess`, aggregate = e.g. `Users`, feature = e.g. `DeactivateUser`)

**Command** (state-changing):
1. `src/Modules/<Module>/Sergin.<Module>.Application.Contracts/<Aggregate>[/<ChildEntity>]/Commands/<Feature>/<Feature>Command.cs` — `public sealed record <Feature>Command(...) : ICommand<<Feature>CommandResponse>;`
2. `.../<Feature>/<Feature>CommandResponse.cs` (same `.Application.Contracts` project) — `public sealed record <Feature>CommandResponse(...);`
3. `src/Modules/<Module>/Sergin.<Module>.Application/<Aggregate>[/<ChildEntity>]/Commands/<Feature>/<Feature>CommandHandler.cs` (note: this file — the handler — stays in `.Application`, not `.Application.Contracts`; only the request/response records from steps 1–2 live in `.Application.Contracts`) — `internal sealed class` implementing `ICommandHandler<TCommand, TResponse>`, primary-constructor-injects `I<Module>UnitOfWork` + the domain repository, calls a domain factory/behavior method, calls `unitOfWork.SaveChangesAsync`, returns the response. When the permission depends on the loaded record (a role is managed at its owner scope, not the caller's current one), the configuration cannot express it: inject `IScopeAuthorization` (`Sergin.SharedKernel.Application.Securities.Authorization`) and return `Error.Forbidden()` after the load when `authorization.CurrentUserHasAsync(<Aggregate>Permissions.X, record.ScopeId, cancellationToken)` is false — `RenameRoleCommandHandler` is the reference.
3b. `src/Modules/<Module>/Sergin.<Module>.Application/<Aggregate>[/<ChildEntity>]/Commands/<Feature>/<Feature>CommandValidator.cs` — every write command gets one: `internal sealed class <Feature>CommandValidator : AbstractValidator<<Feature>Command>` (`using FluentValidation;` per file, not in `GlobalUsings.cs`), rules in the constructor. Commands carry value objects, so target `.Value` and restore the command property name: `RuleFor(x => x.UserName.Value).NotEmpty().MaximumLength(UserName.MaxLength).OverridePropertyName(nameof(CreateUserCommand.UserName));` — the property name becomes `Error.Code`. An optional value object: `RuleFor(x => x.Address!.Value)....When(x => x.Address is not null)`. Put a length limit as `public const int MaxLength` on the value object in `.Domain` and read it from here and from the EF configuration, never as a literal in two places (the Blazor form model reads nothing — it has no attributes; the Blazor page runs this validator live through `ISerginFormValidator`, so keep `.OverridePropertyName(nameof(<Feature>Command.X))` on every `.Value` rule, that is the name the form asks for). Nothing to register — `AddSerginCore` scans `ApplicationAssembly` for `IValidator<>` implementations. Reference: `Users/Commands/Create/CreateUserCommandValidator.cs`, `Devices/Commands/Create/CreateDeviceCommandValidator.cs`.
   **Repository-backed rules** (`using Sergin.SharedKernel.Application.Validations;`) go in the same validator, after the shape rules. Inject the repositories through the validator's constructor — `CreateDeviceCommandValidator(IDeviceRepository devices, IManufacturerRepository manufacturers)` — which is fine because the validator is scoped and lives in the request scope with the `DbContext`. Two shapes, each targeting the **wrapper** (so `Error.Code` is already the property name; no `OverridePropertyName`) and each behind a `.When` on its own shape rule so no query runs for a value already refused:
   - The command references another **aggregate root** → `RuleFor(x => x.OtherId).MustExistIn(others).When(x => x.OtherId.Value != Guid.Empty);` (message `'Other Id' must refer to an existing Other.`; `MustExistIn` is generic over `IRepository<TAggregateRoot, TId>`). The command references an **entity inside another aggregate** (a `DeviceModel` inside `Manufacturer`) → there is no repository for `MustExistIn` to take, so write a local `MustAsync` over a named lookup on the owning aggregate's repository with the same message text: `RuleFor(x => x.DeviceModelId).MustAsync(manufacturers.ModelExistsAsync).WithMessage("'{PropertyName}' must refer to an existing DeviceModel.").When(x => x.DeviceModelId.Value != Guid.Empty);` — `CreateDeviceCommandValidator` is the reference.
   - The command carries an alternate key → `RuleFor(x => x.DeviceId).MustBeUniqueIn(devices).When(x => !string.IsNullOrWhiteSpace(x.DeviceId.Value));` (message `'Device Id' is already in use.`), which requires the repository to declare that key (step 7).
   Both are advisory; the FK / unique index is the guarantee, and a race still throws `DbUpdateException` — don't try to catch it in the handler. A find-or-create command (`ProvisionExternalUser`) gets no uniqueness rule, since the value is legitimately taken by the row the handler is about to find. A command that **adds a child entity to an existing aggregate** (`AddDeviceModel`) gets neither rule: not-found is the handler's (it loads the aggregate and returns `Error.NotFound()`), and uniqueness inside the aggregate is the aggregate's (`Manufacturer.AddModel` returns `Error.Validation` itself). Reference: `Manufacturers/DeviceModels/Commands/Add/AddDeviceModelCommandValidator.cs`.
4. If the domain aggregate needs a new factory method or behavior (e.g. `User.Deactivate()`), add it to the aggregate class in `Sergin.<Module>.Domain`. Don't add public setters — mutate via methods on the aggregate.
5. Presentation: `src/Modules/<Module>/Sergin.<Module>.Presentation.WebApi/<Aggregate>[/<ChildEntity>]/Endpoints/<Feature>/<Feature>Endpoint.cs` implementing `IEndpoint.MapEndpoint`, mapping the appropriate HTTP verb, binding a request model (add one alongside the endpoint if the command needs a body, e.g. `New<X>Model.cs`), sending via `ISender` (`sender.Send(...)`), returning `res.ToApiResult()`. Route strings carry no schema segment (`/devices`, not `/dm/devices`). Call `.Produces<TResponse>()` on Create and GetList endpoints, not on GetOne ones — both modules do this. A versioned endpoint does nothing for `If-Match`/`ETag`: `UseSerginWebApiAsync` adds `ExpectedVersionEndpointFilter` and `AuthorizationScopeEndpointFilter` to the whole module group.
6. Register the endpoint in the module's `<Aggregate>InstallationExtensions.Map<Aggregate>Endpoints` (e.g. `UserInstallationExtensions.MapUserEndpoints`) — instantiate and call `.MapEndpoint(routeBuilder)`. For a brand-new aggregate, create that file first (copy `UserInstallationExtensions.cs`) and wire it into the module class: `services.Add<Aggregate>Dependencies()` in `<Module>Module.AddServices` and `group.Map<Aggregate>Endpoints()` in `<Module>Module.MapEndpoints`.
7. If a new repository interface/dependency is needed, register it in the same file's `Add<Aggregate>Dependencies` (`services.AddTransient<IFoo, Foo>()`). A write-side repository is `internal class <Aggregate>Repository(I<Module>DbContext dbContext) : EfRepository<<Aggregate>, <Aggregate>InternalId>(dbContext), I<Aggregate>Repository` (`Sergin.SharedKernel.Infrastructure.Data.EFCore.Repositories`) — the base supplies `GetAsync`/`ExistsAsync`/`Insert`/`Remove`, so the class holds only named lookups (`Set.SingleOrDefaultAsync(...)`) and may be a one-line declaration with no body when the aggregate has no named lookups (`ManufacturerRepository` was one until its child entity needed `GetWithModelsAsync`/`ModelExistsAsync`). **If the aggregate has an alternate key** (a value object at most one row may carry — `DeviceId`, `UserName`), three things go in the same slice: `IUniqueKeyRepository<TKey>` on the interface (`IDeviceRepository : IRepository<Device, DeviceIntenralId>, IUniqueKeyRepository<DeviceId>`), `public Task<bool> IsTakenAsync(TKey key, CancellationToken cancellationToken = default) => AnyAsync(x => x.Key == key, cancellationToken);` in the class, and `builder.HasIndex(x => x.Key).IsUnique()` in the `IEntityTypeConfiguration` plus its migration (the "After scaffolding" step below). The interface declaration is a promise the index keeps — never ship the first two without the third.

**Query** (read-side, bypasses EF):
Same shape but under `Commands/<Feature>/` still (this repo keeps queries in the `Commands` folder alongside commands — match that, don't invent a `Queries` folder), implementing `IQuery<TResponse>` / `IQueryHandler<TQuery, TResponse>` from `Sergin.SharedKernel.Application.Commands.Queries`. **The query request record and its response record go in `Sergin.<Module>.Application.Contracts/<Aggregate>[/<ChildEntity>]/Commands/<Feature>/`, same as a command's records — only the `<Feature>QueryCommandHandler.cs` class and the `I<Feature>QueryRepository` interface stay in `Sergin.<Module>.Application`.** The handler depends on a dedicated `I<Feature>QueryRepository` interface (returns nullable response, handler maps null to `Error.NotFound()`). Implement that interface in `Sergin.<Module>.Infrastructure/<Aggregate>[/<ChildEntity>]/Repositories/Queries/<Aggregate|ChildEntity>QueryRepository.cs` using `IDbConnectionFactory` + raw SQL against the module's Postgres schema (see `UserQueryRepository.cs` for the `QuerySingleOrDefaultAsync` / `QueryMultipleAsync` Dapper-style pattern) — never use EF Core for reads.

**Request policy** (commands and queries alike). A request that needs a permission or an expected version gets `src/Modules/<Module>/Sergin.<Module>.Application.Configurations/<Aggregate>[/<ChildEntity>]/Commands/<Feature>/<RecordName>Configuration.cs`, namespace `Sergin.<Module>.Application.Configurations.<…>.Commands.<Feature>`, with a `using` of the record's Contracts namespace and of the root's Domain namespace. Never put it in `.Application.Contracts` or `.Application`: only `ConfigurationsAssembly` is read, and `AddSerginCore` refuses a configuration anywhere else. **Bind it to its aggregate root** — `ICommandConfiguration<TRecord, TAggregateRoot>`, as every existing configuration is. The bound root's features choose the scope of the check: a `Scoped()` root is checked on the caller's current scope, an unscoped root on any scope the caller holds the permission. An unbound `ICommandConfiguration<TRecord>` is checked on the current scope; use it only for a request that belongs to no aggregate. `RequireExpectedVersion()` is allowed only on a write whose bound root is `Versioned()`; host start refuses it on a query or on an unversioned root. A request with no configuration has no policy at all — only `ProvisionExternalUserCommand` is like that on purpose. Template (a guarded write; a query calls only `RequirePermissions`):

```csharp
using Sergin.MeterMinder.DeviceManagement.Application.Contracts.Devices.Commands.Update;
using Sergin.MeterMinder.DeviceManagement.Domain.Devices;
using Sergin.SharedKernel.Application.Commands.Configuration;

namespace Sergin.MeterMinder.DeviceManagement.Application.Configurations.Devices.Commands.Update;

internal sealed class UpdateDeviceCommandConfiguration : ICommandConfiguration<UpdateDeviceCommand, Device>
{
    public void Configure(CommandConfigurationBuilder<UpdateDeviceCommand> builder) =>
        builder.RequirePermissions(DevicePermissions.Update).RequireExpectedVersion();
}
```

`ModuleCommandConfigurationTests` pins each module's declarations, the permission scope included (`[InlineData(typeof(GetDeviceAuditQueryCommand), typeof(Device), PermissionScope.Current)]`). Add a row for the new configuration.

**List query** (a paged `GetList` slice) is the same shape with three specifics. The request record derives from `ListQuery<Get<Aggregate>ListItem>` — that generic already implements `IListQuery<TItem>`, so no interface list is needed — declared with an explicit constructor rather than positional parameters. **This is mandatory, not stylistic: every `ListQuery` type is `abstract`, so there is nothing to dispatch without a feature record.** Copy `GetDeviceListQueryCommand.cs`:

```csharp
// Plus Get<Aggregate>ListQueryCommandConfiguration.cs in .Application.Configurations, same relative folder: builder.RequirePermissions(<Aggregate>Permissions.Read);
public sealed record Get<Aggregate>ListQueryCommand : ListQuery<Get<Aggregate>ListItem>
{
    public Get<Aggregate>ListQueryCommand(
        Paggination paggination, Term? term = default, Filtering? filtering = default, Sorting? sorting = default)
        : base(paggination, term, filtering, sorting)
    {
    }
}
```

The handler implements `IListQueryHandler<Get<Aggregate>ListQueryCommand, Get<Aggregate>ListItem>`. The `I<Aggregate>ListQueryRepository` interface takes the **base** `ListQuery`, not the feature record — it only reads `Paggination`. The endpoint builds the record itself: `new Get<Aggregate>ListQueryCommand(request.ToPaggination(), request.Term, request.Filtering, request.Sorting)`.

## Aggregate features

Read the root's `<Root>AggregateFeatureConfiguration` in `.Application.Configurations/<Aggregate>/` before writing the slice. Each feature it declares changes the slice:

| Feature | What the slice must do | Reference |
|---|---|---|
| `Scoped()` | Every raw-SQL read of the table adds `{{ScopeColumns.ReachSql}}` to its `WHERE` and builds its parameters with `ScopeColumns.AddParameters(...)`; a row out of reach is `Error.NotFound()`. Writes need nothing: `ScopeStampInterceptor` stamps the scope on insert. A uniqueness or in-use check reads past the scope filter (`DeviceRepository.InEveryScope`). | `DeviceQueryRepository`, `DeviceRepository` |
| `SoftDeletable()` | Every raw-SQL read adds `deleted_at_utc IS NULL` for each soft-deletable table it reads — the EF query filter does not reach Dapper. A delete slice is `repository.Remove(root)` then save; the interceptor turns it into an UPDATE and cascades to children. A reference that a foreign key used to protect needs a validator rule instead. | `DeleteDeviceCommandHandler`, `DeleteManufacturerCommandValidator` |
| `Versioned()` | The GetOne handler derives from `VersionedQueryHandler<TQuery, TResponse>` and implements `HandleVersioned`; its repository returns `Versioned<TResponse>?` (select `row_version`). A write the user starts from a loaded record calls `RequireExpectedVersion()`. The version never goes on a record. | `GetDeviceByIdQueryCommandHandler`, `UpdateDeviceCommandConfiguration` |
| `Audited()` | The detail view's info button needs a `Get<Aggregate>AuditQueryCommand` (`IQuery<AuditInfo>`, `Commands/GetAudit/`) with its handler, query repository method and configuration. An unscoped root's audit SQL selects `ScopeColumns.UnscopedSelectSql`. | `GetDeviceAuditQueryCommand`, `GetManufacturerAuditQueryCommand` |
| `Permissions(...)` | A new definition goes on `<Aggregate>Permissions` and in this call, or host start refuses the configuration that requires it. | `DeviceAggregateFeatureConfiguration` |

**A new aggregate** gets its own `<Root>AggregateFeatureConfiguration` (`internal sealed`, `IAggregateFeatureConfiguration<Root>`), and its module's `DbContext` must override `AggregateFeatures` (both existing contexts do). Turning on `Audited()`, `SoftDeletable()`, `Versioned()` or `Scoped()` needs a migration in the same PR; the references are `AddAuditColumns`, `AddSoftDeleteColumns`, `AddRowVersionColumns` and `AddDeviceScope` (dm): add the columns nullable, backfill, then make them `NOT NULL`.

**Layout** — `src/Modules/<Module>/Sergin.<Module>.Presentation.Blazor/<Aggregate>[/<ChildEntity>]/`:

| `Components/<Name>.razor{,.cs}` | — | a **non-routable** component (no `@page`): `[Parameter]`s instead of route parameters, otherwise the same `.razor`/`.razor.cs` split, `public sealed partial class` code-behind and `[Inject]` properties as a page. **Every `@page` template must start with `/<schema>/`.** A startup guard in `UseSerginWebUiAsync` reflects over the module's `UiAssembly` and throws, naming the offending component and template, otherwise — Razor `@page` templates are compile-time constants, so unlike minimal-API routes there is no `MapGroup(schema)` to add the prefix centrally. Note this is the opposite of the endpoint rule above, where the route string must *not* include the schema.

**`.razor` holds markup only; every line of C# goes in the `.razor.cs` partial.** Code in an `@code { }` block compiles through the Razor source generator into output the analyzer pipeline doesn't gate — an unaudited hole in a repo where warnings are errors. There are zero `@code` blocks in the repo today; don't be the first.

**Code-behind shape** — `public sealed partial class <Name>View`, property injection (not primary constructors):

```csharp
[Inject]
private ISerginDispatcher Dispatcher { get; set; } = default!;

[Inject]
private IUiErrorPresenter ErrorPresenter { get; set; } = default!;

[CascadingParameter]
private SerginViewHost Host { get; set; } = SerginViewHost.Unhosted;   // only if the view leaves (after save/delete)

[Parameter]
public Guid Id { get; set; }                                           // detail/edit views only
```

A view never injects `NavigationManager` to leave: `await Host.LeaveAsync(href)` lets the host decide (a page navigates; a future dialog host closes).

**Inject `ISerginDispatcher`, never `ISender`/`IMediator`.** In Blazor Server "scoped" is the SignalR circuit's lifetime, not a request's, so a directly resolved `ISender` would share one `DbContext` for as long as the tab is open — unbounded change tracker, stale first-level-cache reads, and "a second operation was started on this context" on parallel renders. `ScopedSerginDispatcher` (`Sergin.SharedKernel.Presentation.Blazor.Dispatching`) opens a fresh scope per send and resolves `ISender` inside it — nothing else; it doesn't pre-check required permissions or branch Local/Remote itself, both of which are `PermissionCheckPipelineBehavior`'s job inside the MediatR pipeline (that pipeline covers a Remote module's calls too, via `RemoteForwardingHandler`). `ISerginDispatcher` is Blazor-only — WebApi endpoints inject `ISender` directly instead (see the endpoint template above).

Three calls, all returning `ErrorOr<T>`:
- `await Dispatcher.SendAsync(new Get<Aggregate>ByIdQueryCommand(Id))` → `ErrorOr<<Aggregate>QueryResponse>`; same call for commands → `ErrorOr<<Feature>CommandResponse>`.
- `await Dispatcher.SendVersionedAsync(request, version)` → `ErrorOr<Versioned<TResponse>>` (`Value.Value`, `Value.Version`). A view over a `Versioned()` root loads through it, holds the version, sends every guarded write at that version and reloads on a stale answer. A row delete reads the version just before it sends. References: `DeviceDetailView`, `DeviceEditView`.
- `await Dispatcher.SendAsync(new Get<Aggregate>ListQueryCommand(Paggination.Create(state.PageSize, state.Page + 1)), cancellationToken)` → `ErrorOr<ListQueryResponse<TItem>>`, whose `.Data` is `IReadOnlyCollection<TItem>` and `.Total` an `int`. There is no list-specific dispatcher helper. **`PageIndex` is 1-based while MudBlazor's `TableState.Page` is 0-based** — hence the `+ 1`, which every existing list page comments.

**Error handling, two shapes** — both go through `IUiErrorPresenter`, which maps the `Error` through the same `SerginProblemFactory` the API uses, so both surfaces render identical text for a given `error.Code`:
- **List page / mutate action** → `ErrorPresenter.Notify(result.FirstError)` (snackbar), and for a list return `new TableData<TItem> { Items = [], TotalItems = 0 }`. **Create submit** → `ErrorPresenter.Notify(result.Errors)` — the list overload, one snackbar per error, because the command validator (step 3b) yields one error per broken rule.
- **Detail page load** → `problem = ErrorPresenter.Present(result.FirstError)` into a `private SerginProblem? problem;` field, rendered by `<SerginProblemPanel Problem="problem" />` in the markup. Set `problem = null` on the success path. This is what makes a required-permission failure or a missing record show up as an inline alert instead of a blank page.

**Every view declares `private IReadOnlyList<SerginBreadcrumb> Trail`** in its code-behind and passes it to its view type (`Trail="Trail"`), which renders the breadcrumb strip and the `<PageTitle>` when hosted by a page. (UserAccess pages, not yet on views, render `<SerginBreadcrumbs Trail="Trail" />` right after their `<PageTitle>` instead.) The trail holds its steps below home, the last being the current page (`Sergin.SharedKernel.Presentation.Blazor.Navigation`, already in both `_Imports.razor` and `GlobalUsings.cs`). The section step is `SerginBreadcrumb.Of(<Module>Navigation.<Aggregate>)`, so **a new aggregate's nav entry is a named `public static SerginNavItem <Aggregate> { get; }` on `<Module>Navigation`, and `Items` is composed from those names** — never a second copy of the label and href. A page under a parent aggregate adds a middle step linking by the route parameter (`new(parent?.Name ?? "<Parent>", $"/<schema>/<parents>/{ParentId}")`), loading the parent for the name if the page does not already. The component prepends Home, localises labels and renders the last step disabled without an href; pages never name Home and never mark the last step themselves. Full rules: root CLAUDE.md "Blazor UI conventions" and `docs/superpowers/specs/2026-09-17-breadcrumbs-design.md`.

**Markup conventions** (copy from the reference views): a list is `SerginAggregateList<TItem>` (or `SerginEntityList<TItem>` for child entities), never a bare `MudTable` — only the ID column links to the detail page, rows are not click targets, and row actions go in `RowCommands`. Multiselect is `BulkActions` with `SerginBulkAction<TItem>`; every delete confirm goes through `IDialogService.ConfirmDeleteAsync`. A form in DeviceManagement is `SerginFormView`, which owns the `MudForm`: the view passes `Model`, `Validation`, `OnSubmit`, `Submitting`, `SubmitLabel` and `CancelHref`, and its `SubmitAsync` starts at the dispatch (`DeviceCreateView`, `DeviceEditView`). The rest of this paragraph is the shape `SerginFormView` renders, and the shape UserAccess pages still write by hand: `<MudForm @ref="form" Model="model" Validation="@validation" @bind-IsValid="isValid" SuppressImplicitSubmission="false" onsubmit="@OnSubmit">` + `MudTextField @bind-Value="model.X" For="@(() => model.X)" Immediate="true"` (a `MudSelect` keeps `For=`, needs no `Immediate`), with the Create button `ButtonType="ButtonType.Submit"` and `Disabled="@(submitting || !isValid)"`. Code-behind for the form, copy from `CreateUserPage.razor.cs`: `[Inject] private ISerginFormValidator FormValidator`, fields `private MudForm form = default!; private bool isValid; private bool submitting; private Func<object, string, Task<IEnumerable<string>>> validation = default!;`, `private EventCallback OnSubmit => EventCallback.Factory.Create(this, SubmitAsync);` (an `EventCallback`, not a bare delegate — splatted onto MudForm's `<form>` it needs a receiver to re-render), `protected override void OnInitialized() => validation = FormValidator.RulesFor(ToCommand);`, one `private <Feature>Command ToCommand()` mapping the form model to the command (used by both the live validation and the submit), and `SubmitAsync` opening with `await form.ValidateAsync(); if (!form.IsValid) { return; }`. `onsubmit` is lowercase with no `@` (an unmatched attribute on the component, splatted onto the real `<form>`; Blazor `preventDefault`s it); `SuppressImplicitSubmission="false"` because MudBlazor 9 defaults it to `true`, which blocks Enter; `Validate()` is obsolete, `ValidateAsync()` is the call; `IsValid` starts `true` (no silent first validation), so the button is disabled *while* invalid, not *until* valid. The validator's `.Value` rules must keep `OverridePropertyName(nameof(Command.X))` — that is the name the form asks for. Never `EditForm`/`DataAnnotationsValidator`, and no validator of the form model itself. Full rationale: root CLAUDE.md "Blazor UI conventions" and `docs/superpowers/specs/2026-09-17-mudform-client-validation-design.md`. **Sort, filter and search need the read side first.** A list control does something only when the feature declares a `ListFieldSet` (`<Aggregate>ListFields` in `.Application.Contracts`), a `ListQueryValidator<TQuery>` subclass next to the handler, and a `ListQueryColumns` map in its query repository that calls `ListQuerySql.Apply` for the count and the page — `DeviceListFields`/`GetDeviceListQueryCommandValidator`/`DeviceQueryRepository` are the reference. A list whose repository does not do that uses `SerginAggregateList` with `Searchable="false"`, no `MudTableSortLabel`s and no `FilterPanel` — a control the repository ignores would silently do nothing.

**Registration** — pages need no DI registration; the module's `UiAssembly` is already scanned. Two follow-ups only:
1. Add a `SerginNavItem` to `<Module>Navigation.Items` for the **list** page (detail/create pages are reached by navigation, not the menu). Existing entries: `new SerginNavItem("Devices", "/dm/devices", Icons.Material.Filled.Router, Order: 100, RequiredPermission: DevicePermissions.Read)`, `new SerginNavItem("Manufacturers", "/dm/manufacturers", Icons.Material.Filled.Factory, Order: 110, RequiredPermission: ManufacturerPermissions.Read)`, `new SerginNavItem("Users", "/ua/users", Icons.Material.Filled.People, Order: 200, RequiredPermission: UserPermissions.Read)` and `new SerginNavItem("Scopes", "/ua/scopes", Icons.Material.Filled.AccountTree, Order: 210, RequiredPermission: ScopePermissions.Read)` — each a named `public static SerginNavItem` property, with `Items` composed from them. `Order` sorts within the module's drawer group (`<Module>Navigation.Group`), not across modules. Pass the `PermissionDefinition` the list query's configuration requires as `RequiredPermission` (it must be registered, or host start refuses it) so the menu hides an entry the user could only 403 on.
2. Add the feature's Contracts namespace (`Sergin.<Module>.Application.Contracts.<Aggregate>.Commands.<Feature>`) to the project's `_Imports.razor` for the markup and to its `GlobalUsings.cs` for the code-behind — DeviceManagement lists every feature in both. Never add a `@using` to an individual `.razor` file.

Permissions are definitions, never strings. A new aggregate defines `public static class <Aggregate>Permissions` in `.Application.Configurations/<Aggregate>/` (`public static PermissionDefinition Read { get; } = PermissionDefinition.Create("permission.<schema>.<resource>.read", "View …");` — the only place a name is a literal) and registers them in its `<Root>AggregateFeatureConfiguration` with `builder.Permissions(<Aggregate>Permissions.Read, …)` (no migration); a configuration may only require a registered definition, and so may a nav `RequiredPermission`, or host start is refused. In `DevUser` mode the configured user is seeded as `administrator` at the root and passes every check, so there is no permission list to edit.

## After scaffolding

1. Check each new project's `GlobalUsings.cs` before adding `using` statements — many namespaces (`ErrorOr`, `Sergin.SharedKernel.*`) are already global. In `.Presentation.Blazor` check `_Imports.razor` as well — it covers the markup, `GlobalUsings.cs` covers the code-behind. A brand-new feature's request/response records live in `.Application.Contracts`, so `.Presentation.WebApi`/`.Presentation.Blazor` reference that project, not `.Application` — don't add a `.Application` `ProjectReference` alongside it for a new feature; the handler-bearing `.Application` project is never a presentation dependency.
2. If the feature needs new/changed columns, add or update the `IEntityTypeConfiguration` in `Sergin.<Module>.Infrastructure.Data`, then generate a migration:
   ```
   dotnet ef migrations add <Name> --project src/Modules/<Module>/Sergin.<Module>.Infrastructure.Data --startup-project src/Hosts/Sergin.MeterMinder.Hosts.All
   ```
   The scaffolded `<Timestamp>_<Name>.cs` comes out with a block-scoped namespace and fails the very next build on IDE0161 (`csharp_style_namespace_declarations = file_scoped` is an error). Convert it to `namespace X;` by hand and dedent the class before building; the `.Designer.cs` and the model snapshot are `<auto-generated/>` and exempt — leave those alone. `AddDeviceIdUniqueIndex` is the converted shape to match.
3. Build to confirm it compiles cleanly — this repo treats every analyzer/style warning as a build error:
   ```
   dotnet build Sergin.MeterMinder.slnx
   ```
4. If the slice added a UI page, run the host and hit the new route — the route-prefix guard and `Sergin:DevUser` validation both fail at startup, before a port opens, so "it starts" is itself a meaningful check:
   ```
   dotnet run --project src/Hosts/Sergin.MeterMinder.Hosts.All   # http://localhost:5002
   ```
   The integration suite (`tests/Sergin.MeterMinder.IntegrationTests.All`) asserts pages render server-side; add an `[InlineData]` route to `Shell/ModulePageRenderingTests.cs` for a new list, create or edit page (detail and edit routes use the fixed ids already in that file).
5. Test the slice. A write gets a test that sends the command through `ISerginDispatcher` resolved from `factory.Services.CreateScope()` — never from the root provider, where the scoped dispatcher throws. Put it in the folder for what it proves (`Scoping/`, `SoftDelete/`, `Concurrency/`, `Validation/`, …), and copy `DeviceManagementConcurrencyTests` or `DeviceManagementSoftDeleteTests` for the shape. A guarded command sent for another reason goes through `VersionedDispatch.SendAt…VersionAsync`. A pure domain rule with no database goes in `tests/Sergin.UserAccess.UnitTests` for UserAccess. The integration suite needs Docker running.

**Still write the endpoint even though no API host runs it.** `Sergin.MeterMinder.Hosts.WebApi.All` was dropped, so nothing calls `MapEndpoints` right now — but both modules still implement `ISerginWebApiModule` and the endpoint layer still compiles, precisely so an API host can be re-added as a ~20-line `Program.cs`. A slice that ships a page but no endpoint quietly breaks that. Its cost is one small file; skipping it costs the whole property.
