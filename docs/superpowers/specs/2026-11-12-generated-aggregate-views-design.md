# Generated aggregate views

Date: 2026-11-12. Status: approved.

## Intent

An aggregate's pages should follow from what the platform already knows about it. Every request record is typed
(`IUpdateCommand<Device, …>`, `IDeleteCommand`, `ITransitionCommand`, `ISelectable`, `IGetOneQuery`, `IListOf`, …), every
configuration says who may send it (`RequirePermissions`), whether it needs a version, and whether it can be scheduled
(`Schedulable(name)`), and every aggregate feature configuration says whether the root is `Audited()`, `Scoped()`,
`Versioned()`, `SoftDeletable()` and which text category labels its fields. Today each view repeats all of that by hand:
`DeviceDetailView` lists its actions, passes each one's permission again, wires `SendVersionedAsync`, the stale reload, the
delete confirm, the Info button, and builds a separate Schedule… button through `SerginScheduleAction.PageAsync`. Twenty-four
views (~4,700 lines across three repos) do this, each a chance to drift from the configuration.

The goal: SharedKernel generates an aggregate's list, detail, create and edit views from the type and configuration
metadata. A module adds only the facts Application cannot know (an action's label and icon, routes, links between
records), and customizes any generated piece when the default is not enough.

The second part, asked for explicitly: a schedulable command's action becomes a **split button**. The main part runs the
command now; the arrow opens the command's menu, which holds **Schedule…** and **View schedules (n)**. The separate
Schedule… button goes away.

## Goals

- Generated by default: actions bar, row commands, selection-bar (bulk) actions, page header buttons, loading, versioned
  sends and stale reload, delete confirm, leave-after-delete/save, permission hiding, breadcrumb trail, detail fields, list
  columns, sort labels, filter panel, create and edit forms, child-entity sections, scheduled-tasks section.
- Customizable at every level, from a single field's rendering to a whole slot, with a hand-written view still possible.
- One place per fact: permissions, version rule and schedulability are read from the existing configurations, never
  repeated in the view configuration.
- Every existing view converted: DeviceManagement (Device, Manufacturer, DeviceModel), UserAccess (User, Role, Scope,
  assignments), Settings (Language, Translation).
- Schedulable commands render as split buttons (option C below) on the detail bar, the selection bar and in row menus.

## Non-goals

- No change to Application-side configuration semantics (`ICommandConfiguration`, `IAggregateFeatureConfiguration`) and no
  UI facts added to them.
- No change to any route. Every URL stays as it is; the `/{schema}/` route guard stays.
- No new effect or target interfaces. If a command does not fit its type today, that is a separate fix.
- No dialog (modal) host for whole views. `SerginDetailOpenMode` keeps only `Page`. (Command dialogs are in scope; see
  "Set-property edit mode".)
- No WebApi or gRPC change.

## Anti-goals (a failure even if it works)

- A view configuration that restates a permission, a version rule or a schedule name. If the view config can contradict
  the Application config, the design failed.
- Metadata recomputed by reflection on every render. Reflection runs once at host start, into a singleton registry.
- A customization that can only be done by copying a generated view's whole source.
- A regression on any pinned behaviour: `PseudoLocaleSweepTests`, `PageTypeRenderingTests`, `BreadcrumbRenderingTests`,
  `ViewHostRenderingTests`, `TreePageRenderingTests`, `ScheduledTaskUiTests` and the rest must still pass (their
  assertions may move to the generated shape, not lose coverage).
- Presentation types (MudBlazor icons, hrefs, UI-only texts) leaking into `.Application.Configurations`.

## Constraints

- `.Application.Configurations` stays UI-free; UI-only texts stay in the RCL (`<Aggregate>UiTexts`), as the 2026-11-07
  design requires.
- `.razor` files markup only; no `@code` blocks. Analyzers gate everything (`TreatWarningsAsErrors`, `AnalysisMode=All`).
- `@page` templates are compile-time constants, so routable page files stay (see "Pages" below).
- `ISerginDispatcher` per send, `SendVersionedAsync` for versioned loads and writes, `IUiErrorPresenter` for errors, as now.
- UserAccess and Settings are submodules: their conversion lands as PRs in their own repos, pointer bumped here.
- Form validation keeps `ISerginFormValidator.RulesFor(ToCommand)` — the pipeline's validator stays the one rule source.

## Decided with the user

1. **Three sources, combined at host start.** Application configs stay as they are; a new presentation-side view
   configuration per aggregate, in the RCL, adds only presentation facts. A view registry reads
   `CommandConfigurationRegistry`, `AggregateFeatureRegistry` and the view configurations, and joins them by request type.
2. **Generate everything, customize anything.** Fields, columns, filters and forms are generated too; the developer can
   override any of them.
3. **Split button, option C.** A schedulable command is a split button: main part runs the command; arrow opens a menu
   with Schedule… and View schedules (n). The menu is the command's general "more" place, open to module-added items.
   Plain button (no arrow) when the command is not schedulable or the user lacks `permission.sys.scheduled-tasks.manage`.
4. **Convert everything**, including the four views that fit no generic shape — `TranslationListView` (inline translation
   grid), `RoleDetailView` (permission picker), `ScopeDetailView` + `ScopeTreeLayout` (tree), `UserAssignmentsView`. Those
   become generated pages whose special part is a custom slot declared in their view configuration, which is how the
   customization path is proven on the hardest cases.
5. **Set-property edit mode is configurable per command**, default Dialog; Inline and Page are the other modes.

## Design

### The view configuration

One `internal sealed class <Root>ViewConfiguration : IAggregateViewConfiguration<Root>` per aggregate root, in the RCL's
aggregate folder (next to `<Aggregate>UiTexts`). Child entities are configured inside their root's configuration, the
same way aggregate features are. Discovered by scanning each `ISerginWebUiModule.UiAssembly` in `AddSerginBlazorApp`.

```csharp
internal sealed class DeviceViewConfiguration : IAggregateViewConfiguration<Device>
{
    public void Configure(AggregateViewBuilder<Device> view)
    {
        view.Title(DeviceUiTexts.Title)
            .Routes(list: "/dm/devices", detail: id => $"/dm/devices/{id}", create: "/dm/devices/new",
                    edit: id => $"/dm/devices/{id}/edit");

        view.Command<ReadDeviceProfileCommand>()
            .Label(DeviceUiTexts.ReadProfile)
            .Icon(Icons.Material.Outlined.Sensors)
            .SucceededText(DeviceUiTexts.ReadProfileDone);   // Schedule… comes from Schedulable(...) by itself

        view.Detail(detail => detail
            .Field(d => d.DeviceModelName).Link(d => $"/dm/manufacturers/{d.ManufacturerId}/models/{d.DeviceModelId}")
            .Field(d => d.ManufacturerName).Link(d => $"/dm/manufacturers/{d.ManufacturerId}"));

        view.List(list => list.Overview<DeviceOverviewCards>());   // a module component in a slot
    }
}
```

What the view configuration may say: titles, routes, per-command label/icon/success text/confirm texts, per-field
rendering (link, format, component, hidden, order), extra menu items on a command, slot components, form field
overrides (picker source, cascading pickers, a custom input component). What it may **not** say: permissions, scope,
version rule, schedule name — those are read. The builder has no method for them.

### The view registry

`AggregateViewRegistry` (singleton, built in `AddSerginBlazorApp`) holds one `AggregateViewModel` per configured root:

- **Requests by role**, from `CommandTypes.TargetOf`/`EffectsOf` over every Contracts assembly: the GetOne query
  (`IGetOneQuery`), list query (`IListOf`), overview queries, audit query (`IAuditQuery`), create command, update command,
  delete command, transitions (with `IReverseOf` pairs), set-property commands, move command, child list/add/remove/update
  per child type, entity-view queries.
- **Per request**, from `CommandConfigurationRegistry.For`: required permissions, `PermissionScope` (→ `AnyScope`),
  `RequiresExpectedVersion`, `ScheduleName`; from `CategoryOf`/`HiddenProperties` and `TextCatalog.FindField`: field labels.
- **Root features**, from `AggregateFeatureRegistry`: `Audited` (Info button shows audit), `Versioned`, `Scoped`
  (Info scope line, `AnyScope`), `SoftDeletable`.
- **Response shapes**: GetOne response and list item properties, labelled by `FieldText` in the root's category; the list
  query's `ListFieldSet` for sortable columns and filter modes.
- **The view configuration's presentation facts**, joined by request type.

Built once at start; nothing reflects per render.

**Start guard** (refuses host start, naming each type, like `CommandTypeGuard`): a view configuration naming a request
not typed to its root; two view configurations for one root; an action-producing command with no label where no default
exists (defaults exist for create, update, delete, add/remove child — `CommonTexts`; a transition or set-property command
must declare its label); a configured root missing a GetOne query or list query its routes promise; a field override
naming a property the response does not have.

### Generated views

New SharedKernel components that take the root's model from the registry and render through the existing view types
(`SerginAggregateListView`, `SerginAggregateDetailView`, `SerginEntityListView`, `SerginFormView`), so host, header slots,
breadcrumbs and outlines behave exactly as today:

- `SerginGeneratedListView<TRoot>` — overview (if an overview query exists or a slot is set), actions bar (create),
  `SerginAggregateList` with columns from the list item, sort labels and filter panel from `ListFieldSet`, row commands,
  bulk actions for `ISelectable` commands and delete.
- `SerginGeneratedDetailView<TRoot>` — versioned load through GetOne, header (reload, copy link, Info when audited), fields
  from the response, actions bar, child-entity sections, scheduled-tasks section when the root has any schedulable command.
- `SerginGeneratedFormView<TRoot>` — create (from the create command) and edit (from the update command, loaded versioned).
  Inputs generated from the command's shown properties: text for string-backed value objects, number, date, bool switch,
  enum select, and a picker for a typed id that names another aggregate or child (options from that root's list query or
  the child's list query; depends-on pickers declared in the view configuration, e.g. manufacturer → model).
- `SerginGeneratedChildSection<TRoot, TChild>` — embedded entity list for a child (DeviceModels under Manufacturer):
  add, rename/update, remove (at the root's version), bulk remove.
- `SerginGeneratedChildDetailView<TRoot, TChild>` and `SerginGeneratedChildFormView<TRoot, TChild>` — the child's own
  routed pages (today `/dm/manufacturers/{ManufacturerId}/models/new`, `/{Id}` and `/{Id}/edit`), loaded through
  `IChildGetOneQuery`, written through `IAddChildCommand` / the child update or set-property command, at the root's
  version. The child's routes are declared inside the root's view configuration and carry the root id:
  `view.Child<DeviceModel>(child => child.Routes(detail: (rootId, id) => …, create: rootId => …, edit: (rootId, id) => …))`;
  the route start check covers them like the root's. (Decided by Claude after the review: "convert everything" and
  "no route changes" together require it.)

The generic parameter is the root type; components resolve the request and response types from the registry and build
requests by constructor. A command whose only shown properties are its target ids (transitions, delete, read-profile) is
built from the id alone. Any other command (update, set-property) goes through a form, or a confirm dialog for a delete
with extra shown properties (e.g. `Cascade`). Creating the request object from a record is the one place reflection
touches runtime; the constructor is found and cached at start.

### Actions

The registry maps each command to a `SerginPageAction` (detail bar), a `SerginBulkAction<TItem>` (selection bar, for
`ISelectable`), and a row-menu entry:

| Effect | Where | Kind | Behaviour |
|---|---|---|---|
| `ICreateCommand` | list bar | Primary | link to create route |
| `IUpdateCommand` | detail bar, row icon | Secondary | link to edit route |
| `ITransitionCommand` | detail bar, row menu, bulk if `ISelectable` | Secondary | send; reverse pair shows the one that applies (state from the response, declared in view config) |
| `ISetPropertyCommand` | detail bar (Dialog, Page) or the field itself (Inline) | Secondary | edit mode per command, default Dialog (see below) |
| `IMoveCommand` | detail bar | Secondary | parent picker dialog |
| `IDeleteCommand` | detail bar (far end), row icon, bulk | Danger | confirm, versioned send, leave to list |
| `IAddChildCommand` / `IRemoveChildCommand` | child section | Primary / Danger | as `DeviceModelListView` today |

Each action carries the permission and `AnyScope` read from configuration. Versioned sends use the version the view
holds; a stale answer reloads.

### Set-property edit mode

A set-property command (and a child's) edits one value. How is configurable per command in the view configuration,
`.Command<RenameScopeCommand>().Edit(SerginEditMode.Inline)`, with three modes (decided with the user, default Dialog):

- **Dialog** (default) — an action on the detail bar opens a `MudDialog` holding one input, validated through
  `ISerginFormValidator.RulesFor` like any form, sent at the held version; the view reloads after.
- **Inline** — the input sits in the detail body: a small form card for a text value (today's Rename scope/role/language),
  or the field itself made editable for a choice (today's Set language direction), read-only for a user without the
  permission.
- **Page** — a routed form page (today's `/dm/manufacturers/{ManufacturerId}/models/{Id}/edit` for Rename device model);
  the action links to the route the view configuration declares.

Converted commands keep today's behaviour by declaring it: Rename scope, role and language and Set language direction
`Inline`, Rename device model `Page` (its route must stay). (Claude's call, so that no visible behaviour changes in the
conversion; switching any of them to the Dialog default later is one line.) The "no dialog host" non-goal means opening
a whole detail view as a modal; command dialogs like this one and the Schedule dialog are in scope.

### Split button and command menu (option C)

`SerginPageAction` and `SerginBulkAction<TItem>` gain `MenuItems` (a list of `SerginMenuItem(Label, Icon, OnClick,
Permission, AnyScope)`). `SerginActionBar` and the selection bar render an action with menu items as a `MudButtonGroup`:
the main button plus an arrow `MudMenu`. With no visible menu item it renders as today's plain button. Row commands put
the same items in the row's `SerginActionMenu`.

For a command with `ScheduleName`, the generator adds two items, both visible only when the user holds
`ScheduledTaskPermissions.Manage` on the current scope **and** the command's own permission:

- **Schedule…** — opens `SerginScheduleDialog` (existing) with the command template built from the id, targets = the
  record (detail) or the selection (bulk), target labels from the record's display field.
- **View schedules (n)** — scrolls to the detail page's `SerginScheduledTasksSection` and filters it to this command.
  `SerginScheduledTasksSection` gains a `CommandName` filter parameter and exposes its per-command count. On the list
  page and in bulk this item is omitted (no section there).

A view configuration can add its own items to any command's menu (`.MenuItem(...)`), which also turns a non-schedulable
command into a split button.

`SerginScheduleAction.PageAsync`/`BulkAsync` are deleted; the separate Schedule… buttons go with them.

### Enum values

Enum-typed properties (`Status`, `Direction` on Language) get value texts declared in Application next to the field,
through a new `TextCategory` helper keyed by member (`Category.Values<LanguageStatus>(…)`, keys
`<category>.values.<enum>.<member>`). A shown enum property with no declared value text refuses host start, extending
`FieldTextGuard`; `catalog-keys.txt` grows by the new keys. Settings' hand-written `LanguageLabels` map is deleted.
(Decided by Claude after the review: Application already owns field texts and the guard, and a request or response can
carry an enum without any UI.)

### Customization ladder

From least to most:

1. **Declare** in the view configuration: labels, icons, routes, field links/format/order/hidden, picker sources, extra
   menu items, hide a generated action (`.Command<X>().Hidden()` — presentation only, the command stays callable).
2. **Replace a piece** with a component: one field (`.Field(x => x.Y).Component<T>()`), one form input, one column.
3. **Fill or replace a slot**: Overview, Fields, Entities, an extra section, HeaderActions extras, the whole body —
   `.Detail(d => d.Slot<T>(SerginSlot.Entities))`. The slot component receives the loaded record, the version and a
   reload callback as parameters.
4. **Hand-written view**: a module may still write a view on the existing view types; the page then hosts it instead of
   the generated one. Allowed, but every view in this repo is converted, so none exists after this work.

The four special views use rung 3: their special part (translation grid, permission picker, tree, assignments) becomes a
slot component on a generated page.

### Pages

`@page` must be a constant, so each module keeps thin page files: `@page "/dm/devices/{Id:guid}"`,
`@layout SerginPageLayout`, `<SerginGeneratedDetailView TRoot="Device" Id="Id" />`. Route templates and the guard stay
as they are; the view configuration's `Routes(...)` must agree with the page templates, which a start check verifies by
matching each configured route against the `[Route]` attributes in the module's `UiAssembly`. (Builder's call whether a
source generator can emit these files later; not in scope.)

### Trees

Scopes keep `ScopeTreeLayout` and `SerginAggregateTree`; the node detail page becomes `SerginGeneratedDetailView<Scope>`
inside the layout, keeping the `Pane` host and `SerginTreeSelect` hand-over. The move command's action uses the tree's
parent picker.

### Rollout order

Each step leaves the app working and the full test suite green.

1. SharedKernel: registry, view configuration builder, start guard, split button / menu items, scheduled-tasks section
   filter, generated list/detail/form/child components. Tests with test-only aggregates.
2. DeviceManagement: Device (proves split button with Read profile), then Manufacturer with DeviceModel child section.
3. Settings: Language, then Translation (custom grid slot).
4. UserAccess: User and assignments, Role (permission picker slot), Scope (tree).
5. Delete the hand-written view files, `SerginScheduleAction`, and update CLAUDE.md files (root, SharedKernel, the
   modules') and the `/add-feature` and `/add-module` skills to describe the view configuration instead of hand-written
   views.

SharedKernel, UserAccess and Settings changes land as PRs in their repos; the pointers are bumped here.
